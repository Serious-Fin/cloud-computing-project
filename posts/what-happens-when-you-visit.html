What actually happens when someone visits your site

You type a URL and press enter. A few hundred milliseconds later a page appears. In between, several distinct systems each do one small job. Knowing the order helps when something is slow or broken.

Step one: DNS turns a name into an address

The browser needs an IP address. It asks a DNS resolver, which walks the domain hierarchy until it finds a record for your domain. For a site on a CDN this is usually an A record pointing at the provider's anycast address, or a CNAME pointing at a provider hostname.

This lookup is cached at every layer — browser, operating system, resolver — for as long as the record's TTL allows. That is why a DNS change can seem to work for you but not for someone across the world.

Step two: a connection, then a handshake

With an address in hand the browser opens a TCP connection and, for HTTPS, performs a TLS handshake. The server presents a certificate proving it owns the domain, both sides agree on encryption keys, and everything after that is encrypted.

Modern setups combine these steps and can reuse previous sessions, which is why a repeat visit is noticeably faster than the first one.

Step three: the edge answers

On a CDN your request lands on a server physically near the visitor rather than one in a single data centre. Anycast routing means many machines advertise the same address and the network quietly delivers to the closest.

That edge server checks its cache for the requested file:

  • Cache hit — the bytes go straight back. This is the common case.
  • Cache miss — the edge fetches from the origin, stores a copy, then responds.

Step four: the origin, if needed

The origin is where the real content lives. For a static site that is usually object storage or a build artefact store. A well-cached site might touch the origin a handful of times a day.

Cache headers decide how long a copy stays valid. Too short and you pay for every visit. Too long and your updates take a while to appear.

Step five: the browser renders

The HTML arrives and the browser starts parsing it immediately. Each linked stylesheet or script triggers another request, so the number of files on the critical path matters more than the size of any single file. 

DNS  →  TCP + TLS  →  Edge cache  →  (Origin)  →  Browser paints
 20ms     60ms          ~0–10ms       ~100ms        variable

Where things go wrong

  1. Stale DNS. A record change has not propagated yet.
  2. Expired certificate. Nobody automated renewal.
  3. Cache poisoning. An old file is cached where you did not expect.
  4. Missing asset. A single 404 on a stylesheet can make the page look broken.

None of these are exotic. Each becomes easy to diagnose once you know which layer in the chain is responsible.
