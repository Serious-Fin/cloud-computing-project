The smallest useful deploy checklist

Long checklists get skipped. This one has five items, and the last is the one that actually saves you.

1. Do you know what is changing?

Not the commit message — the actual effect. "Update stylesheet" is not an answer. "The header shrinks on mobile so the nav stops overlapping the title" is. If you cannot say it in one sentence, the change is probably too big to deploy alone.

2. Is it verified somewhere that is not your laptop?

Preview deployments make this nearly free: open a pull request, get a live URL, click through it on a real phone. Local testing misses case-sensitive paths, missing files, and anything that depends on the real domain.

3. Are broken links going to 404?

Renamed a page? Search the project for the old path before you deploy. A 404 in production is a broken promise to whoever clicked it, and it is cheap to catch beforehand. 

# Find leftover references to a renamed file
grep -rn "old-page.html" --include="*.html" .

4. Is there a cache trap?

If long cache headers are set on assets that keep the same file name, visitors will hold on to the old version. Rename the file or version it in the query string. New name, new cache entry.

5. How do you undo it?

The most useful thing to know about a deploy is how to reverse it.

Ask this before you need it, not at midnight. On Netlify, atomic deploys mean the previous version is still intact — open the Deploys list, choose the one you want, and publish it. No rebuild, no rebuild failures, no scrambling.

That is the whole list

  1. You can state the change in one sentence.
  2. It has been tested somewhere real.
  3. No links are broken.
  4. No stale cache will serve the old file.
  5. You know how to roll back.

Five items, and the last one turns a scary operation into a boring one. Boring is the goal.
